# M11f — Aura-unique features

Part of [M11](m11.md). Soft tip `c69e644`.

## M11f — sandbox worlds for AI tries (`soft/pad/world.aura`, `PAD_M11_WORLD_OK`)

**What the kid sees.** The kid has a goal: three checks such as "hello 3
is 6". The helper brings up to three ideas. They are tried somewhere
else, and the page does not flicker. Then one line says how it went:

> the helper tried 3 ideas in its own worlds: idea 1 passes 3 of 3 checks (your page 1 of 3), kept it. ctrl-z takes it back

> the helper tried 2 ideas in its own worlds, none did better than your page (1 of 3 checks), nothing changed

Only an idea that passes strictly more checks than the page comes back.
It comes back as a normal robot KEEP, with one ctrl-z, "who" stamps, and
a time-machine step.

**How.**
1. `pad:world-race! who ideas goal` takes an `ast:snapshot` of root and
   scores the goal on the page as it is now.
2. Each idea goes through the Soft gate first. A gated idea never gets a
   world. Each other idea then:
   - gets `workspace :create "try-k"` + `:switch` (the child starts as a
     copy of root's program, so there is no `set-code` and no load cost);
   - goes in as one `typed-mutate-atomic` under the helper's fingerprint;
   - has its goal checks run in the child.
3. Back home after every idea: `workspace :switch 0`, then `ast:restore`
   of the root snapshot + one `eval-current`. A child's rebind changes the
   shared top-level bindings, and once a child has run `eval-current`,
   root's own `eval-current` does not put root's bindings back
   (aura#4368, filed). Without the heal, the next idea and the page would
   run the last idea's code.
4. The winner is KEPT by `pad:robot-step!` in root: `mutate:rebind` of
   the winning defines, the M11a transaction. `workspace :merge` is never
   used, because it concatenates source and leaves duplicate defines.
5. Checks against the engine (any mismatch prints `M11_WORLD_DISAGREE`):
   - per idea, the defines that differ between root's `query:code` and
     the child's (the Soft split of both canonical programs from
     `time.aura`) are exactly the idea's names;
   - `workspace:conflicts-with` lists them too. On c69e644 it lists every
     define the two worlds share, so this is only a superset check;
   - root code and the page object are unchanged after the tries;
   - after the KEEP, root `query:code` equals the winner's child code,
     and the goal score in root equals the winner's score.

**Measured on the tip.**
- `WORLD base=1 ideas=1:tried:3:hello/add.bye.greet.hello.pad-nb-rows.pet,2:tried:2:hello/…,3:refused:-1 win=1 same=yes verdict=agree`
  (`hello/` is the engine-changed names, after `/` what
  `workspace:conflicts-with` listed).
- After ctrl-z, `(hello 3)` in root is 4 again (`F1_UNDO_HELLO`).
- With no winner, `(greet 1)` in root is still 2, and `workspace
  :current` is 0 (`F2_GREET_ROOT`, `F2_ROOT_CURRENT`).

**Limits.**
- Every idea leaves one child in `workspace :list` (`children=` in
  M11STATS). `workspace:discard` is not a removal: its documented meaning
  is "reset the child to the parent's state", and the child stays listed.
  `workspace:delete` does remove it, but a child's rebind leaks into
  root's bindings even without a child `eval-current`. After the delete,
  root can then hold a binding into the freed child: SIGSEGV on the next
  call, or a hang after `workspace:discard`. In the race loop it can also
  give a vector assert on the next `:switch` (aura#4369, filed). So
  children are kept until that is fixed.
- Ideas run one after another, not in parallel: fibers gave no speedup
  on pure code (aura-vs-rust p09).
- A refused idea scores -1 and gets no kid reason. Reasons stay with the
  M11c path, when the helper proposes directly.
- Like the other robot paths, this lives on the notebook face, so key
  latency is unchanged.
