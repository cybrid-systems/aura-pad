# M11 — Aura-unique features for kids

The ranked list in [`aura-vs-rust.md`](aura-vs-rust.md) Part 3 names the
features only Aura's live, transactional, attributable workspace AST makes
cheap. M11 builds them in order on the notebook stack (`ws.aura`,
`pen.aura`, `who.aura`, `who_pen.aura`). The play loop (`play.aura`) does
not load that stack, so key latency is unchanged (`smoke_perf.sh`). Soft
owns every decision; C only blits.

```bash
bash scripts/smoke_m11.sh    # PAD_M11_TEST_OK + UNDO / WHO / WHY / BLAST markers (also run by smoke.sh)
```

Every API below was re-checked on Soft tip `c69e644` before use
(probes in `out/m11/p/`, not committed).

## M11a — "undo the robot" (`soft/pad/robot.aura`, `PAD_M11_UNDO_OK`)

**What the kid sees.** The helper proposes a change that touches several
defines (for example `hello` and `bye`). Either all of it lands or none
of it does. Afterwards **ctrl-z** (`IN 26`) takes the whole change back
in one key: both rows, the engine code and the "who wrote this" stamps.
A broken proposal never half-lands. The say line explains what happened:
"the helper changed hello and bye, ctrl-z takes it all back" or "aura
said no to the whole change, nothing moved".

**How.**
1. The Soft pen gate (`pad:pen-gate`) checks every edit first: kind
   words, locked words, `(lambda` only, a name born in the notebook, at
   most 4 edits, no name twice. A NO never takes a snapshot or calls the
   engine.
2. `ast:snapshot`, then **one** `typed-mutate-atomic` call with one
   `(mutate:rebind "name" "lam" "why")` sexpr per edit. The engine runs
   them under one MutationBoundary. `query:mutations-since` shows every
   record of the proposal with the same non-zero `composite=` id. The
   post-mutate typecheck runs too: arity errors are refused in every
   gate mode, type errors under `AURA_MUTATE_TYPE_GATE=hard`.
   `run_soft.sh` now passes that variable through, and `smoke_m11.sh`
   sets it to `hard`.
3. KEEP: every edited one-line define is projected into the page
   (`pad:pen-project`) and stamped `helper/why/gen`. The snapshot is
   pushed with the page.
4. ctrl-z: `ast:restore` plus one `eval-current` (aura#4349/#4361),
   then the page goes back too. Engine code and page must both equal the
   pre-proposal state, otherwise `M11_UNDO_DISAGREE` fails the smoke.
5. Refused: `ast:restore` plus `eval-current` anyway (a failed batch
   can leave stale node ids, #4361). The page is untouched and nothing
   is pushed.

**Measured on the tip.**
- A two-define KEEP bumps the workspace generation by 2 and the
  mutation total by 4.
- A refused proposal changes neither (`gen+=0 total+=0`). The good half
  of the proposal is absent from `query:code` (`A3_ADD_NOT_HALF`,
  `A3_HELLO_NOT_HALF`).
- Notebook procedures still answer after a refusal (`A3_CALLABLE`).

**Why not `mutate:atomic-batch`?** It returns a reason value, but on
`c69e644` it **skips the type and arity gate** in both modes: a batch
commits a rebind that `mutate:rebind` refuses. Filed as
[aura#4362](https://github.com/cybrid-systems/aura/issues/4362).
`typed-mutate-atomic` gates, but it answers only `#t` / `#f`, so M11c
recovers the kid reason separately.

**Not a transaction:** `ws:try-mutation` rolls back only when its body
*raises*. A refused `mutate:rebind` inside it returns a value, and an
earlier rebind in the same body stays committed (probe `p2`). The pad
does not use it.

## M11b — engine-level "who wrote this" (`soft/pad/eng_who.aura`, `PAD_M11_WHO_OK`)

**What the kid sees.** ctrl-o (`IN 15` on the notebook face,
`pad:robot-line!`) on a define row answers from aura's own log, not
from a pad guess: "the AI helper wrote hello: closer (change 2)", "a law
wrote greet: rule (change 6)", "the AI helper wrote hello, then you
changed it". Rows nobody changed, and rows that start no define, keep
the M10 answers ("nobody has changed this yet", "you wrote this line").

**How.**
1. Every robot transaction (M11a) and every pen step
   (`pad:ew-pen-step!`, which wraps M10's `pad:who-pen-step!`) runs
   under `mutate:set-agent-fingerprint`: kid=1, helper=42, macro=3,
   law=4. The fingerprint goes back to kid right after. The engine copies
   it onto every record of the transaction (`author=42` in
   `query:mutations-since`).
2. ctrl-o finds the define that starts on the cursor row (Soft tokens),
   then asks the engine:
   - `define-lookup name` gives the node id;
   - `query:node-provenance id` gives `author-fingerprint`,
     `mutation_id` and `gen` (`mutation_id` 0 means no write since the
     check);
   - the newest `op=rebind` record for that node in
     `query:mutations-since 0` gives the reason (`sum=`).
3. Cross-check with the M10 Soft stamp of the row:
   - `agree`: same writer and same reason, or no engine write while the
     Soft stamp is kid or none (kid typing reaches the engine at the
     next check);
   - `kid-after`: the engine writer wrote the define, then the kid typed
     on the row;
   - `soft-only`: the row starts no define (engine granularity is the
     define node);
   - `disagree`: anything else. It prints `M11_WHO_DISAGREE` and fails
     the smoke.
4. Undo needs nothing extra. `ast:restore` puts node provenance *and*
   the mutation log back to the snapshot. After a robot change by a
   helper and then one by a macro, the first ctrl-z leaves the helper's
   `add` at helper and returns the macro's `hello` to nobody (probe
   `p5`, test `B2`). The fingerprint is process state and is not
   restored, so the pad always sets it explicitly.

**Measured on the tip.**
- `EWHOROWS 0=hello:helper:agree.1=bye:helper:agree.2=add:nobody:agree.4=pet:nobody:agree.5=greet:law:agree`
  after a helper robot KEEP and a law pen KEEP.
- No `disagree` on any row across KEEP, two undos, and kid typing.
- The checker flags forged Soft stamps: wrong writer, wrong reason, a
  stamp missing where the engine has a write, and a stamp present where
  the engine has none (`B3_FORGED_*`).

**Limits.** The fingerprint is an integer label, not a principal
(aura#4037 in the source). Provenance is per define node, so the M10
Soft stamps still answer for rows that start no define.

## M11c — "why did it break?" in kid words (`soft/pad/why.aura`, `PAD_M11_WHY_OK`)

**What the kid sees.** When aura refuses a helper's change, the say line
names the define that broke and says why in one short sentence, instead
of a bare "no":

| aura's own reason (c69e644) | say line |
|---|---|
| `type error: argument 1: expected String, got Int` in the new body | the helper's greet used a number where words go |
| `arity mismatch: call 'hello': expected 1 arguments, got 2` in the new body | the helper's bye gives hello 2 things, it wants 1 |
| the same, blamed on a line that *uses* the changed define | the helper's hello now wants 2 things, but bye gives it 1 |
| `type error … blamed: caller` on `(bye 4)` | the helper's bye does not fit (bye 4) |
| `unbound variable: frob` | the helper's bye uses frob, nothing is called that yet |
| `parse-error … unexpected ')'` | the helper's bye has a bracket in the wrong place |
| a missing `)` (the engine closes it silently, probe `p8`) | the helper's brackets do not match (Soft gate, before any snapshot) |

**How.**
1. `typed-mutate-atomic` answers only `#f`. So after a refusal, *before*
   the robot's heal, `pad:why-probe!` replays the proposal one
   `mutate:rebind` at a time. The first refusal gives aura's text. The
   replay can commit the good edits ahead of the bad one, but the
   robot's single `ast:restore` + `eval-current` puts them back. Tests
   check one heal per refusal, unchanged code and page, and that
   notebook procedures still answer.
2. A Soft table turns the text into a sentence:
   - it finds the kind (arity / type / unbound / brackets);
   - it reads the names and numbers out of the text;
   - it maps type names to kid words (String → words, Int → a number,
     a type variable → something else).
   If the 1-based line after `(selective) failed:` holds a call to the
   changed define and is not that define's own row, aura is blaming a
   caller. The sentence then names that line: the define it starts, the
   row text if it is short, otherwise "line N".
3. After a KEEP, `typecheck-incremental` lines go through the same
   table. On the tip they only show up as "aura warns: …" when they are
   real.
   - `unbound variable: X` is dropped when `X` is a notebook define.
     `typecheck-incremental` reports value defines like `pet` as
     unbound, and after a refused rebind it still shows diagnostics from
     the refused body. Filed as
     [aura#4363](https://github.com/cybrid-systems/aura/issues/4363).
   - `C3_TC_SAID_PET` checks that the false line really came, and
     `C3_NO_FALSE_WARN` checks that the kid never saw it.

**Measured on the tip.**
- Every refusal in the tests gives the sentence in the table above
  (`C2_*`, `C3_CALLER_TYPE_SAY`).
- The replay costs one extra rebind per edit up to the bad one. It runs
  only on refusals, never on the key path.

## M11d — "blast radius" card before KEEP (`soft/pad/blast.aura`, `PAD_M11_BLAST_OK`)

**What the kid sees.** With the card path (`pad:robot-card!`), a helper
idea does not land right away. The say line shows what it would move,
and the page stays as it is:

> changing add moves 3 places: greet, (greet (add 1 2)), (add 2 3). enter keeps, ctrl-z says no

**Enter** keeps it, exactly like an M11a KEEP: rows projected, a ctrl-z
undo entry, "who" stamps. **ctrl-z** says no: "ok, the helper's idea is
gone, nothing changed". A proposal aura refuses never shows a card; the
kid gets the M11c reason instead.

**How.**
1. The proposal goes through the same gate and the same one
   `typed-mutate-atomic` inside an `ast:snapshot` (M11a). On `#t` it
   *waits* (`*robot-pending*`): the engine has the change, the page does
   not.
2. Soft builds the page the KEEP would give (`pad:pen-project`). It
   finds every call site of the changed names, meaning a name right
   after `(` that is not a define head, and drops the changed defines'
   own rows. Each remaining row is named by the define it starts, by its
   text when short, or as "line N". At most 3 are shown, then "and N
   more".
3. The engine checks that answer:
   - `query:calls name` must find as many call sites as Soft did, per
     name. After a rebind the engine also keeps the replaced body's
     sites (aura#4364, filed). In that case the engine must have added
     exactly the call sites the new bodies hold. The counts are taken
     before and after the transaction: `sites=hello:3/4:+1` means Soft
     finds 3, the engine says 4 (stale), and the engine added 1, which
     is the `(hello y)` in the new `bye`;
   - per page define, `query:defines name` plus `query:dirty-subtree`,
     before and after the transaction. The defines whose dirty count
     grew must be changed names, and every changed name must be dirty
     now. After a rebind, `query:dirty-nodes` marks only the rebound
     define node and the root (probe `p11`), so callers never show up
     as dirty.
   - A mismatch prints `M11_BLAST_DISAGREE` and fails the smoke.
4. Enter calls `pad:robot-commit!`, the same code as an M11a KEEP.
   ctrl-z calls `ast:restore` + `eval-current`. One heal, and nothing is
   pushed for undo.

**Measured on the tip.**
- `BLAST names=hello.bye uses=6.7.11 sites=hello:3/4:+1.bye:2/2:+0 grown=hello.bye dirty=hello.bye verdict=agree`.
- While the card waits, the page object is unchanged (`D1_PAGE_WAITS`)
  and `query:code` already has the change (`D1_ENGINE_HAS_IT`).

**Limits.** c69e644 has no node → row query, so the rows come from
Soft and the engine confirms the counts. `query:reaches` (def-use) and
`query:calls` give node ids, not rows. Like every robot path, the card
lives on the notebook face, not in `play.aura`, so key latency is
unchanged.
